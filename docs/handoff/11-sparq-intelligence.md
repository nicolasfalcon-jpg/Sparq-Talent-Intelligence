# 11 · Sparq Intelligence (the Claude gateway)

Phase C. `ClaudeAssistant` (src/features/ask-sparq/llm/claude.ts) implements the same `AssistantGateway` contract as the rule-based gateway. The route, the request resolution and every authorization rule are unchanged.

> **Verification status.** Everything below is tested with a **fake** Anthropic client (`tests/unit/llm-*.test.ts`). **No call to the real API has been made**: the real model path (output quality, latency, whether the structured output and tool schemas are accepted as written) is unverified until `ANTHROPIC_API_KEY` is configured and the primary journey is run once by a person.

## Flow
`POST /api/assistant` → session (401) → strict Zod body → `resolveAssistantRequest` (context, suggestion, subject, **page context** authorized) → gateway:
1. **Policy pre-check** (`assessTalentRequest`) on free text: a declined request (ranking, scoring, weakest, traits, autonomous decisions) never reaches the model and gets the deterministic decline.
2. Actors with no tools (delivery leads, admins) get the deterministic gateway; no model, no quota.
3. **Per-user daily limit**, counted before the call. Over the limit → **HTTP 429**, no model call. If usage cannot be counted → no model call, deterministic answer (never unlimited).
4. Bounded tool loop (read-only, as the actor) → strict JSON answer → Zod + **output policy check** (`assessModelOutput`: no percentages, ratings, "score", "rank", superlatives about people) → refs validated against what the tools returned → provenance `ai`.
5. **Any failure** (error, timeout, refusal, invalid or policy-violating output) → the deterministic answer, provenance `fallback`, with an honest notice.

## Honesty rules
- `ai` is set **only** when a real model produced the answer; the UI shows "Generated by Claude from documented data, not a decision" and the model id. `computed` / `illustrative` / `fallback` are never labelled AI.
- The evidence line next to a person always comes from tool data (source and verification), never from model text. Unknown refs are dropped.
- **No automatic fallback to another model or provider, and the server-side `fallbacks` parameter is not used.** A refusal is shown through the deterministic answer, labelled `fallback`.
- No write tools: the assistant never proposes, assigns, shortlists or edits. Proposed ≠ assigned.

## Tools (all read-only; arguments validated by Zod; run as the actor through `scopedTalent` / the policy)
| Tool | Who | Returns |
|---|---|---|
| `search_talent_by_requirements` | staffing lead | people with documented experience per requirement (source + verification), ordered by `matchPeople`, no score |
| `get_authorized_evidence` | staffing lead (any), engineer (own) | evidence rows and projects; never interests or preferences |
| `get_opportunities_and_roles` | staffing lead (all); engineer (Open only, no proposals, no delivery lead) | opportunities, roles, seat state |
| `check_availability` | as above | free-from, confirmed/pending, fit for a kick-off |
| `analyze_team_coverage` | staffing lead | documented / training-or-independent / not documented / waiting groups |
| `explain_allocation_conflicts` | staffing lead | whether a window and allocation fit (peak ≤ 1.0), existing assignments |

A tool the actor may not use, an unknown tool, bad arguments or an unreadable person all return the same generic error: no reasons, no data. Offering a tool is only a hint to the model; **execution re-checks authorization every time**, so a manipulated or injected model gains nothing. Profile, project and opportunity text is wrapped as `<tool_data untrusted="true">` (forged delimiters stripped) and the system prompt says it is data, not instructions.

## Contextual intelligence
Ask Sparq works from every page; Fill a Role, Build a Team, Compare and Planning have "live from this page" prompts (`content.ts`). A page publishes what is on screen with `usePublishAssistantContext({ opportunityId, seats })` (`page-context.ts`); the panel attaches it only where `context-rules.ts` allows, and the server **re-authorizes** the opportunity and every person (`access.ts`), rejecting it elsewhere. Without a key those prompts are answered deterministically (`gateway.ts`).

## Configuration (server only)
| Variable | Meaning | Default |
|---|---|---|
| `ANTHROPIC_API_KEY` | enables the Claude gateway | unset → rule-based |
| `SPARQ_ASSISTANT_PROVIDER` | `rules` forces the deterministic gateway | – |
| `SPARQ_ASSISTANT_MODEL` | model id | `claude-sonnet-5-5` |
| `SPARQ_ASSISTANT_EFFORT` | `low` / `medium` / `high` (`output_config.effort`) | `low` |
| `SPARQ_ASSISTANT_DAILY_LIMIT` | model calls per user per UTC day (1–1000) | `40` |

Bounds: 25 s total budget (shared `AbortSignal`), ≤ 4 tool rounds, `max_tokens` 2000, one SDK retry. Sonnet 5.5 rules respected: no forced `tool_choice`, no `thinking: disabled`, no prefill, no sampling parameters. The key is read only in `service.ts`; a test fails if a client component or any other module touches it.

Usage limit: memory mode keeps a per-process counter; Supabase mode calls `consume_assistant_quota(p_limit)` through the request-scoped client (migration owned by the db workstream).

## Limits
The policy detector and the output check are heuristics (see 08 §6); the output check is intentionally strict, so a legitimate answer can be replaced by the deterministic one. Model quality and latency are unmeasured. Per-process counters reset on restart and are not shared across serverless instances (use Supabase mode for a real limit).
